## 起点：一个很烦的问题

之前我的博客用的是某开源 CMS。写一篇文章的流程是：

1. 打开浏览器，登录后台
2. 新建文章，选分类、填标签、传封面
3. 在富文本编辑器里写，或者把 Markdown 粘进去让编辑器转一遍
4. 点保存，等它转存到数据库
5. 发现写错了，回后台改，再点保存

第 3 步是灾难：富文本编辑器会**吃掉你的格式**。有序列表变成无序列表，代码块变成灰底段落，表格直接散架。想写一篇带代码的文章，得在编辑器里跟它搏斗。

## 换个视角

某天我意识到：我真正在做的事情是 —— **版本化地维护一批文本文件**。

这件事 Git 已经解决了，而且解决了二十年。我为什么要在上面再套一个功能更弱、还更不可控的层？

于是重新设计：

```
写作  →  在本地新建 .md 文件
预览  →  npm run dev，Vite HMR 实时刷新
发布  →  git commit && git push
撤回  →  git revert
草稿  →  front-matter 写 draft: true
版本  →  git log content/posts/xxx.md
```

## 这些原本是"功能"，现在是"副作用"

对照一下。后台系统需要专门开发的特性，在这个工作流里是不存在的——因为它不需要存在：

| 后台系统里的功能 | Git 工作流 |
| --- | --- |
| 草稿箱 | `draft: true`，构建时过滤 |
| 修订历史 | `git log -p` |
| 回滚到某个版本 | `git checkout <sha> -- file.md` |
| 定时发布 | `date` 字段 + 构建时比较当前时间 |
| 多端同步 | `git pull` |
| 内容备份 | 每个 clone 都是一个完整备份 |
| 协作 | branch + PR |
| 变更审计 | `git blame` |

注意最后几条：**内容审计和版本回滚，是 CMS 做得最烂的地方**。多数后台的"历史版本"只留最近几版，回滚按钮点下去还未必干净。Git 在这方面是工业级工具。

## 目录即分类

一个具体的设计决定：**用目录结构承载分类**，而不是在 front-matter 里声明。

```
content/
└── posts/
    ├── 前端/
    │   ├── vue-component-patterns.md
    │   └── vite-optimization.md
    ├── 后端/
    │   └── node-performance.md
    └── 随笔/
        └── on-writing.md
```

好处很直接：

- **移动文件就是改分类**，不需要打开文件编辑元数据
- **`ls` 就能看到分类结构**，不依赖任何工具
- 新建文章时，`mkdir` 就是"创建分类"
- Git diff 里，改分类表现为一次 rename，语义清晰

代码里从路径反推分类：

```js
function categoryFromPath(path) {
  const m = path.match(/content\/posts\/(.+)\/[^/]+\.md$/)
  return m ? m[1] : '未分类'
}
```

放在根目录下的文章自动归入「未分类」，不用强制建目录。

### 那标签呢？

分类是**唯一**的（一篇文章只能在一个目录里），标签是**多值**的。两者不是一回事，所以标签留在 front-matter：

```yaml
category: 前端          # 由目录决定，一般不用手写
tags: [Vue, 性能优化, 构建]
```

这个区分很重要：分类回答"这是哪一类东西"，标签回答"这篇跟什么有关"。前者是归档维度，后者是检索维度。

## 一个必须解决的细节：排序

文件名排序 ≠ 时间排序。用日期前缀能解决：

```
2026-09-12-vue-markdown-blog.md
```

但这让 URL 变丑。我的做法是文件名只作标识，排序完全依赖 front-matter 的 `date`：

```js
posts.sort((a, b) => b.date.localeCompare(a.date))
```

`YYYY-MM-DD` 格式的字符串可以直接字典序比较，比 `Date` 对象更快也更省事——但前提是**补零**。`2026-9-5` 和 `2026-09-12` 直接比会得到错误结果。

## 什么时候这套会崩

诚实地说，三个场景：

1. **多人写同一个仓库** —— 会有冲突。冲突能解，但非技术作者看到 `<<<<<<<` 会懵。这时候要么上 CMS，要么配个 Web 编辑器（比如 Decap CMS，它本质上是给 Git 仓库套了个 UI）。
2. **手机写作** —— 手机上提交 Git 不现实。可以用 GitHub 网页版，体验凑合。
3. **文章量过万** —— 构建期把全部内容内联进 bundle 就不合适了。那时候该上服务端渲染或者内容 API。

在这三条边界之内，这套工作流非常舒服。

## 结论

**别为低频操作建后台。**

写博客这个行为，一周可能就几次。为它维护一套服务端系统，投入产出比是负的。而 Git 是现成的、免费的、经过二十年验证的版本控制——你只需要把仓库的目录结构设计好。

真正的收益不是省了服务器钱，而是：**内容的所有权和控制权都在你手上**。格式不会被编辑器篡改，历史不会被悄悄覆盖，平台倒了文章还在。
